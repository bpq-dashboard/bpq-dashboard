Health check — is everything running?

Start here when something looks broken. System Audit runs these checks for you (services, timers, parsers, status files) and says which are not installed; the commands below do the same by hand over SSH. Services you never switched on (for example bpq-vara or vara-validator) report inactive; that is normal.

systemctl is-active nginx php8.3-fpm mariadb bpq bpq-telnet bpq-chat bpq-aprs bpq-vara vara-logger vara-validator rig-history-poller
One word per service, in this order. Anything that should be on and says inactive or failed: look at its log (next row), then restart it. On Debian 12 PHP is 8.2, so use php8.2-fpm (ls /run/php/ shows yours). bpq is the LinBPQ service name used in these examples.
check all
sudo journalctl -u bpq-telnet -n 50 --no-pager sudo systemctl restart bpq-telnet
Read the last 50 log lines of one service, then restart it. Replace bpq-telnet with the service you are fixing. For nginx, run sudo nginx -t before restarting.
log + restart
nginx
Web server. Down = no pages at all.
php8.x-fpm
Runs every .php file. Down = pages load but show 502 / no data.
mariadb
Database. Down = Email Client, RF Connections, Traffic and System Logs show errors or fall back to slow log parsing.
bpq
LinBPQ itself. Down = no RF, no BBS, no forwarding.
bpq-telnet
Telnet Client page and YAPP transfers (WebSocket 127.0.0.1:8765).
bpq-chat
Chat page. Stays logged in to BPQ chat and re-enters by itself after BPQ's 2-hour idle disconnect (2026-10-24). See Chat.
bpq-aprs
APRS map data (APRS-IS feed) and the optional BBS beacon to aprs.fi. See APRS map & beacon.
bpq-vara
VARA HF Terminal page (WebSocket 127.0.0.1:8767).
vara-logger
Writes the VARA log file the RF Connections parser reads. Down = RF Connections stops getting new sessions.
vara-validator
Optional callsign allowlist in front of VARA HF (127.0.0.1:9025/9026).
rig-history-poller
Optional. Records TX power / SWR history even with no browser open (RF Power Monitor charts).
systemctl list-timers message-bodies.timer bulletin-retention.timer nws-auto-post.timer --no-pager
The timers (not services): message text saved every 5 minutes, the daily bulletin clean-up, and (optional) automatic NWS bulletins every 5 minutes. NEXT should be within 5 minutes, 24 hours and 5 minutes. Details in Email Client, Bulletin retention and NWS auto-post.
timer
cat /etc/cron.d/bpq-dashboard; sudo crontab -l -u www-data
The scheduled jobs. The installer puts the three log parsers in /etc/cron.d/bpq-dashboard; older or hand-built installs keep them in www-data's crontab. Each parser must appear once: the same job in two places (or in root's crontab too) runs twice. Check root with sudo crontab -l.
schedule
sudo ss -tlnp | grep -E ':(80|443|3306|8008|8010|8011|8765|8767|9025|12345)\b'
Listening ports: 80/443 nginx, 3306 MariaDB (should show 127.0.0.1), 8008/8010/8011 LinBPQ web/telnet/FBB, 8765 bpq-telnet, 8767 bpq-vara, 9025 vara-validator, 12345 flrig. A missing line means that program is not running or not listening.
ports
ps aux | grep -E 'linbpq|bpq-(telnet|chat|aprs|vara)|vara-|flrig' | grep -v grep
The actual processes. Use this when systemd says active but a page still says the daemon is not connected; look for duplicates or a restart loop (a PID that keeps changing).
processes

Admin login — keep these pages password-protected

Everything under /admin/ (this page, Firewall, Log Viewer, System Audit and their APIs), install-check.php and health-check.php sit behind one web-server login stored in /etc/nginx/.bpq-mgmt-auth. The status box at the top of this page tests it each time the page opens. The Partners editor also asks for the BBS password from config.php.

The same login guards everything that reads your mail or acts as the station: the Email Client (page, bbs-messages.php, message-storage.php), NWS posting, Chat, and writes to APRS, station locations and the callsign cache (reads stay public for the maps). Those PHP files also refuse on their own unless nginx passes fastcgi_param BPQ_WEB_LOGIN $remote_user; from a location with the login, so a hand-made config can't leave them open. If one answers "needs the dashboard admin login", Install Check's Login reaches PHP and Station-acting pages behind the login rows say what's missing (2026-10-04).

curl -s -o /dev/null -w '%{http_code}\n' -A 'Mozilla/5.0' https://bpq.example.com/admin/bpq-maintenance.html curl -s -o /dev/null -w '%{http_code}\n' -A 'Mozilla/5.0' 'https://bpq.example.com/admin/partners-api.php?action=validate' curl -s -o /dev/null -w '%{http_code}\n' -A 'Mozilla/5.0' https://bpq.example.com/install-check.php curl -s -o /dev/null -w '%{http_code}\n' -A 'Mozilla/5.0' https://bpq.example.com/health-check.php
Run from any machine. All four must print 401 (login required). 403 also means blocked (a LAN-only rule). 200 means anyone can open it: fix the web-server config (next rows) before doing anything else. Keep -A 'Mozilla/5.0': the bot filter answers curl's own user agent with 403, which would look like a pass. From the server itself, add --resolve your.host:443:127.0.0.1 if your router doesn't loop back.
test: no login
curl -s -o /dev/null -w '%{http_code}\n' -A 'Mozilla/5.0' -u ADMIN_USER https://bpq.example.com/admin/bpq-maintenance.html
Same page with the login. curl asks for the password (so it stays out of shell history). Expect 200.
test: login
sudo nginx -T 2>/dev/null | grep -n -A6 'location ^~ /admin/'
Shows the nginx block that protects the folder. It must contain auth_basic and auth_basic_user_file /etc/nginx/.bpq-mgmt-auth, plus a nested location ~ \.php$ with its own fastcgi lines (without it the APIs stop running as PHP). No output = the folder is not protected: copy the block from bpq-dashboard.conf or re-run install.sh. Older configs protected /bpq-maintenance.html etc. one by one at the top level; that no longer covers anything, since the pages moved to /admin/.
nginx
grep -n -B1 -A4 '/admin>' /etc/apache2/sites-enabled/*.conf
Apache installs: the <Directory …/admin> block must have AuthType Basic and Require valid-user.
apache
sudo htpasswd -B /etc/nginx/.bpq-mgmt-auth ADMIN_USER
Change a user's password (bcrypt). Prompts twice. Never add -c here: it wipes the file and every other user with it. Takes effect on the next request, no reload needed.
change password
sudo htpasswd -B /etc/nginx/.bpq-mgmt-auth NEWUSER sudo htpasswd -D /etc/nginx/.bpq-mgmt-auth OLDUSER
Add a second admin, or remove one. The same file also guards the /bpq-mgmt/ BPQ web-management proxy if you use it.
users
sudo cut -d: -f1 /etc/nginx/.bpq-mgmt-auth; ls -l /etc/nginx/.bpq-mgmt-auth
Lists the user names only (never the hashes). The file should be root:www-data 640 or similar, and must be outside the web root. If it's missing, nginx answers 500 on every admin page, which fails closed.
inspect
sudo chown root:www-data /etc/nginx/.bpq-mgmt-auth && sudo chmod 640 /etc/nginx/.bpq-mgmt-auth
Every admin-login page answers 500 and the error log says open() "/etc/nginx/.bpq-mgmt-auth" failed (13: Permission denied): the file is root:root, so nginx's workers (www-data) can't read it. Installers before 2026-10-30 left it that way. No reload needed. fix-permissions.sh does the same.
fix 500
for p in config.php db-config.php bbs-config.php includes/bootstrap.php scripts/bpq_db_config.py data/partners.json sql/2026-07-messages-schema.sql docs/SESSION-JOURNAL.md config.php.bak-test; do printf '%-36s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code} %{size_download}B' -A 'Mozilla/5.0' https://bpq.example.com/$p)"; done
Private files must never download. Every line should be 403 or 404. A 200 whose size equals your home page is a catch-all try_files … /index.php fallback, not the file; any other 200 is a leak. config.php and db-config.php return nothing even when reachable, but should still be 403.
private files
More than one site name on the same web root?
Test every name. The status box above only checks the address you opened this page on. A second server block that shares the folder but has no /admin/ rule serves these pages with no login. Give it location ^~ /admin/ { return 301 https://your-protected-host$request_uri; } (and the same for install-check.php and health-check.php), as in bpq-dashboard.conf. Re-run the curl tests with each name.
two hosts
Reach these pages from outside your network?
The login is the minimum. Use HTTPS, so the admin password isn't sent in clear text, and consider a LAN-only rule as a second layer: add the allow/deny lines from nginx-maintenance-block.conf inside your existing location ^~ /admin/ block.
advice
grep -n -A2 "'cors'" /var/www/bpq-dashboard/config.php
Since 2026-10-20 other web sites can't call the dashboard's endpoints (callsign lookups, proxies, BBS logins) from their visitors' browsers. Expect 'allow_all' => false; list a site in 'allowed_origins' only if it really embeds the dashboard. Install Check and System Audit warn when allow_all is true.
cors

Firewall & System Audit — read-only sudo rules

The Firewall and System Audit pages read the firewall (IPv4 and IPv6), fail2ban, the listening ports and nginx -t through six read-only sudo rules in /var/www/bpq-dashboard/www-data-tools.sudoers. install.sh offers to install them. Without them those rows say "not checked" (they never guess), and everything else on both pages still works.

sudo cp /var/www/bpq-dashboard/www-data-tools.sudoers /etc/sudoers.d/www-data-tools && sudo chmod 440 /etc/sudoers.d/www-data-tools && sudo visudo -c
Install or update the rules. visudo -c must say every file is parsed OK. Copy it again after an upgrade: a rule must match the command exactly, and the 2026-10-25 version replaced rules that no longer matched what the pages run (fail2ban-client is in /usr/bin; iptables now lists all chains so ufw and fail2ban rules are followed).
install
sudo -u www-data sudo -n /usr/sbin/iptables -L -n --line-numbers -v | head -3 sudo -l -U www-data
Runs one rule as the web server would, then lists every rule www-data has. Chain INPUT (policy …) = working; a password is required = that rule is missing or its path differs (command -v iptables ip6tables fail2ban-client ss nginx shows the real paths; edit the file to match).
test
Older rule files
Earlier versions suggested /etc/sudoers.d/www-data-iptables or www-data-audit. They are harmless but no longer used; once the new file works: sudo rm -f /etc/sudoers.d/www-data-iptables /etc/sudoers.d/www-data-audit.
note

Database & credentials

Database settings live in /var/www/bpq-dashboard/db-config.php (or the db section of config.php). No program file contains the password. PHP pages read it through tprfn-db.php, the Python parsers through scripts/bpq_db_config.py.

sudo -u www-data php -r 'require "/var/www/bpq-dashboard/tprfn-db.php"; tprfn_db()->query("SELECT 1"); echo "DB OK: ", TPRFN_DB_USER, "@", TPRFN_DB_HOST, "/", TPRFN_DB_NAME, " from ", tprfn_db_settings()["source"], "\n";'
Connects exactly the way the web pages do, as www-data. Prints who it connected as and which file the settings came from. An Access denied error means the password in db-config.php doesn't match the database.
test php
sudo -u www-data python3 -c 'import sys; sys.path.insert(0, "/var/www/bpq-dashboard/scripts"); import pymysql, bpq_db_config as c; pymysql.connect(**c.load_db_config()).close(); print("DB OK from", c.cfg_source[0])'
Same test for the Python log parsers. No module named pymysql: sudo apt install python3-pymysql.
test python
ls -l /var/www/bpq-dashboard/db-config.php /var/www/bpq-dashboard/config.php sudo chown www-data:www-data /var/www/bpq-dashboard/db-config.php && sudo chmod 640 /var/www/bpq-dashboard/db-config.php
Both files hold passwords: owner www-data, mode 640, never world-readable. fix-permissions.sh and the installer set both (and any older bbs-/nws-/tprfn-/bpqdash-config.php) to 640; System Audit warns if one is world-readable.
permissions
sudo mysql bpqdash -e "SHOW TABLES;"
Expected groups: bpq_* (Email Client), rf_* (RF Connections), traffic_* (Traffic), sys_* / rms_* / tcp_events / net_* (System Logs). A missing group means its schema was never loaded; install-check.php names the file to load.
inspect
sudo mkdir -p /root/db-backups && sudo sh -c 'mysqldump --single-transaction bpqdash | gzip > /root/db-backups/bpqdash-$(date +%F).sql.gz' && ls -lh /root/db-backups/
Back up the whole database before upgrades or schema changes. Keep dumps under /root (or any folder the web server doesn't serve), never in the web root.
backup
sudo mysql -e "ALTER USER 'bpqdash'@'localhost' IDENTIFIED BY 'CHANGE_THIS_DB_PASSWORD';" sudo nano /var/www/bpq-dashboard/db-config.php
Change the database password, then put the same value in db-config.php. The command starts with a space so bash (with the usual HISTCONTROL=ignoreboth) doesn't save it in history (or run sudo mysql and type it at the prompt). Re-run both tests above afterwards.
rotate password

Log parsers — RF Connections, Traffic, System Logs

Three scripts read the BPQ logs into the database every 5 minutes, so those pages load fast. If a page shows (DB) but the data is old, start here.

tail -n 5 /var/log/bpq-dashboard/parse-*.log
Last lines of each parser log (installer layout). Older installs log to /var/log/parse-*.log. A Traceback or Access denied line points at the problem; "notes an in-flight session at end of file" from the VARA parser is normal.
logs
sudo -u www-data python3 /var/www/bpq-dashboard/scripts/parse-vara-log.py --dry-run --verbose
VARA sessions → rf_connections. Dry run: reads and reports, writes nothing. The cron line also passes --bbs-log-dir and --my-callsign for message tracking; keep them when you copy it.
dry run
sudo -u www-data python3 /var/www/bpq-dashboard/scripts/parse-traffic-report.py --days 8 --dry-run --verbose
BPQ traffic reports → traffic_stats. BPQ writes one Traffic_YYMMDD.txt per week (named for the week start, written the following Saturday), so the cron line needs --days 8; without it every run logs "Processed 0 file(s)".
dry run
sudo -u www-data python3 /var/www/bpq-dashboard/scripts/parse-system-logs.py --dry-run --verbose
BBS / TCP / CMS / NetROM logs → the System Logs tables. Safe to run any time; it never double-counts.
dry run
sudo -u www-data python3 /var/www/bpq-dashboard/scripts/parse-vara-log.py --reset --verbose
Rebuild the RF Connections table from the whole VARA log (after a parser fix or a corrupted table). Takes a while on a big log. For Traffic and System Logs the equivalent is --backfill.
rebuild
sudo mysql bpqdash -e "SELECT log_file, last_line_no, last_parsed_at FROM rf_parser_state; SELECT MAX(session_start) AS newest_session FROM rf_connections;"
Where the VARA parser has got to. last_parsed_at should be minutes old; newest_session should match your last VARA contact.
freshness
systemctl status vara-logger --no-pager; ls -l /var/www/bpq-dashboard/logs/*.vara
vara-logger feeds the VARA parser. The .vara file's time should move whenever VARA is active. If the parser reads the wrong file, check logs.vara_file in config.php.
source
ss -uln | grep ':514 '; grep VARAHF /var/log/syslog | tail -3; cat /etc/rsyslog.d/10-bpq-dashboard-vara.conf
Is VARA HF's log arriving? VARA HF (registered) sends it as syslog: Settings → VARA Setup → Syslog, Host = this server, UDP port 514, Station Name H-<call-SSID>. The first command shows rsyslog listening on UDP 514; the second the newest VARA lines; the third which senders the installer's receiver accepts ($AllowedSender). Nothing in syslog: check VARA's Syslog settings, the allowed address and the firewall (UDP 514 from the VARA computer). Installation Manual §10.11.
syslog
logger -n 127.0.0.1 -P 514 -d -t VARATEST "receiver test"; sleep 1; grep VARATEST /var/log/syslog | tail -1
Tests the receiver itself from this server (the VARATEST tag keeps it out of the VARA log). If this line appears but VARA's don't, the problem is on the VARA computer's side or the firewall.
test
sudo crontab -l -u www-data | grep nodes-rtt; ls -l /var/www/bpq-dashboard/logs/nodesrtt.txt
Optional NetROM round-trip times for System Logs: nodes-rtt.sh (every 10 min) writes nodesrtt.txt, which parse-system-logs.py picks up.
optional

Email Client — message database

Personal, NTS and bulletin messages, folders and the address book live in MariaDB (bpq_messages, bpq_msg_folders, …) through message-db.php. Message text is saved too (every 5 minutes by message-bodies.timer, and when a message is opened), and folders pinned with 📌 keep their copies after a Kill on the BBS.

sudo -u www-data php -r '$_SERVER["REQUEST_METHOD"]="GET"; $_SERVER["PHP_SELF"]="/message-storage.php"; $_GET["action"]="stats"; chdir("/var/www/bpq-dashboard"); include "/var/www/bpq-dashboard/message-storage.php";'
Calls the storage API directly on the server, bypassing the browser and login. Should print success:true with counts. Use it when the Email Client shows a storage or database error.
test
sudo mysql bpqdash -e "SHOW COLUMNS FROM bpq_msg_folders LIKE 'keep_on_kill'; SHOW COLUMNS FROM bpq_messages LIKE 'killed_on_bbs_at';"
Both lines must come back. If either is missing, 📌 pins quietly do nothing (the code falls back to the old behaviour). Fix: sudo mysql bpqdash < /var/www/bpq-dashboard/sql/2026-09-26-message-keep-and-bodies.sql (safe to run twice).
schema
sudo mysql bpqdash -e "SELECT msg_type, COUNT(*) AS total, SUM(is_archived) AS shown, SUM(body IS NOT NULL AND body <> '') AS with_text, SUM(killed_on_bbs_at IS NOT NULL) AS kept_after_kill FROM bpq_messages GROUP BY msg_type;"
Per type (P personal, T NTS, B bulletin): shown = still listed (is_archived = 1; Kill sets it to 0), with_text = body saved, kept_after_kill = killed on the BBS but kept by a 📌 folder.
inspect
sudo mysql bpqdash -e "SELECT f.name, f.keep_on_kill AS pinned, COUNT(m.id) AS messages FROM bpq_msg_folders f LEFT JOIN bpq_messages m ON m.folder_id = f.id GROUP BY f.id ORDER BY pinned DESC, messages DESC;"
Every folder, pinned ones first, with its size. Pinned groups keep bulletins forever, so busy groups like NEWS or WX keep growing; unpin them in the Email Client if that matters. The folder limit is 200 (message-db.php).
folders
sudo mysql bpqdash -e "SELECT bbs_number, msg_type, from_call, subject FROM bpq_messages WHERE is_archived = 0 ORDER BY id DESC LIMIT 20;"
Recently killed messages. If a killed message comes back after a reload, check here: the BBS kill can succeed while the database update fails.
troubleshoot
sudo mysql bpqdash -e "SELECT m.bbs_number, m.from_call, LEFT(m.subject,40) AS subject, m.first_seen_at, LENGTH(m.body) AS chars, m.killed_on_bbs_at FROM bpq_messages m JOIN bpq_msg_folders f ON f.id = m.folder_id WHERE f.name = 'Bulletins - SITREP' AND m.is_archived = 1 ORDER BY m.first_seen_at DESC LIMIT 30;"
For "opens with no text": which messages in one folder have their text saved (chars NULL or 0 = only the listing was saved). Change Bulletins - SITREP to the folder you are checking. A message whose text was never saved and is gone from BPQ cannot be recovered; one still on BPQ gets its text the next time it is opened.
diagnose
systemctl list-timers message-bodies.timer --no-pager; sudo journalctl -u message-bodies.service -n 12 --no-pager
The job that saves message text every 5 minutes, whether or not the Email Client is open. Each run ends with one line: listed, text saved, not on BBS, number reused, errors. Details per message: logs/message-bodies.log. Bulletins saved: config.php 'messages' => ['bulletin_text' => 'all'] (or 'pinned', 'none').
status
sudo systemd-run --uid=www-data --gid=www-data --unit=message-bodies-backfill php /var/www/bpq-dashboard/scripts/fetch-message-bodies.php --backfill; sudo journalctl -u message-bodies-backfill -f
Catch-up: asks the BBS for the text of every saved message that has none, newest first, in the background (Ctrl+C only stops watching). Messages BPQ no longer has, or whose number now holds another message, are skipped and not asked for again. Add --days=30 to limit it, --dry-run to only count.
catch-up
"⚠ killed on BBS" label
Since 2026-10-12 it means the message is really gone from BPQ: its number was missing from inside the latest listing (the newest 50 per type, Settings → max list), a read from the BBS came back "not found" or as a different message (BPQ reuses numbers), or a 📌 folder kept it after a Kill. Messages that have only scrolled out of the listing are no longer labelled (before, they were, and their text was never fetched). Opening a labelled message still shows its text if the database has it. Kill on a labelled bulletin skips the "only forwarded (BF) bulletins" safety check. Copies kept by a 📌 folder are never killed on the BBS a second time.
know this
sudo -u www-data php /var/www/bpq-dashboard/scripts/check-nts-messages.php --days=180
For "NTS traffic isn't showing up": lists every NTS row, flags Personal rows that look like misfiled traffic (from before the 2026-08 fix), and shows what a report date range would return.
diagnose
sudo mysql bpqdash -e "SELECT name FROM bpq_msg_folders WHERE name REGEXP '^Bulletins - [0-9]';"
Bulletin folders with garbled names such as "Bulletins - 1 ARNR" (a parser bug fixed in 2026-08). Should return nothing. If it does, use Email Client → Settings → Clean up Bulletin folders, which repairs them in place.
diagnose
"The BBS is busy" / a wait before Get Mail
Only one BBS login at a time (2026-10-12): the Email Client and the message-text job share the lock cache/bpq-telnet.lock, and a new login waits until 2 s after the last one ended. The job's sessions are short, so the page normally waits seconds; after 40 s it says the BBS is busy. If it says so all the time, look for a stuck job: systemctl status message-bodies.service.
note

Bulletin retention

Once a day bulletins older than 14 days are deleted, unless they are in a 📌 pinned group or in a folder you made yourself. Bulletins in Trash go on the next run. Personal mail and NTS traffic are never deleted. The same rule runs from the Email Client's Settings button.

sudo -u www-data php /var/www/bpq-dashboard/scripts/purge-old-bulletins.php --dry-run
Shows what the next run would delete, per folder, without deleting. One-off window: add --days=N. Check that no pinned group appears in the list.
dry run
sudo -u www-data php /var/www/bpq-dashboard/scripts/purge-old-bulletins.php
Runs the clean-up now. This is a real DELETE, not the Kill soft-delete; take a database backup first if you are unsure.
run now
sudo journalctl -u bulletin-retention.service -n 30 --no-pager
What the scheduled runs deleted. If the timer is missing: sudo cp /var/www/bpq-dashboard/bulletin-retention.{service,timer} /etc/systemd/system/ && sudo systemctl daemon-reload && sudo systemctl enable --now bulletin-retention.timer.
log

NWS automatic bulletins (optional)

Every 5 minutes nws-auto-post.timer posts the first issue of each new NWS Warning or Watch for one state as a bulletin (SB, e.g. WX@GA). No updates or cancellations, nothing already ended, never the same alert twice; a watch issued by several NWS offices becomes one bulletin. Settings: config.php 'nws' => ['auto_post' => [...]] (enabled, area, destination, events, exclude). Installation Manual §10.4.

sudo journalctl -u nws-auto-post.service --since today --no-pager | grep nws-auto-post:
One summary line per run: active alerts, warnings/watches, already posted, holding (waiting for other offices' pieces of a watch), posted, failed. Posted bulletins: posted to WX@… lines. Full detail and the BBS dialogue: logs/nws-auto-post.log (Log Viewer → NWS auto-post).
status
sudo -u www-data php /var/www/bpq-dashboard/scripts/nws-auto-post.php --dry-run
What would be posted right now, and why each other alert is skipped. Posts and records nothing. Add --verbose to a normal run for the same detail.
dry run
sudo -u www-data php /var/www/bpq-dashboard/scripts/nws-auto-post.php --seed
Marks every alert active now as posted, without posting. Use after turning the feature on (or after a long outage) when you don't want the alerts already in force to go out.
seed
sudo systemctl enable --now nws-auto-post.timer
Start it after setting 'enabled' => true and 'area' => 'XX'. If the timer is missing: sudo cp /var/www/bpq-dashboard/nws-auto-post.{service,timer} /etc/systemd/system/ && sudo systemctl daemon-reload (the ExecStart path in the .service must be your web root). Stop: 'enabled' => false or sudo systemctl disable --now nws-auto-post.timer.
enable
Posted, but no other BBS gets it
The bulletin goes to the flood area in destination. If none of your forwarding partners carries that area (BPQ Mail → each partner's AT / HR routing), it stays on this BBS. Check one in BPQ Mail's web management → Messages: it should be queued for the partners. "BBS not reachable" failures are retried every run while the alert is in force; any other failure at most 3 times (state: cache/nws-auto-post-state.json).

NTS forwarding report
